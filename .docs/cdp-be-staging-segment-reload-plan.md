# `cdp-be` staging segment reset and 1M test load

## Goal and ownership

Use a disposable `cdp-be` staging test database to serve the approved segment catalogue and one million synthetic members. `cdp-be` lists segments and evaluates selections and counts only when requested. It does not run a member refresh, build, or bitmap-generation worker. A separate, repeatable load process prepares the source rows and any derived artifacts, validates them, and publishes one READY build. Keep an asynchronous job only for a requested full ID export.

This is a test load, not a release of real member data. Do not reset a shared staging database or the separate v1 `segments` feature. Preserve the existing `cdp-be` migration history; add forward migrations after `000058` for the new v0 read model.

## Steps and load order

1. **Settle IDs, rules, and expected results.** Use the [attribute option seed](../services/ecodai/migrations/000004_attribute_segments.up.sql) as the catalogue source. Compare it with [staging's existing v0 seed](../../cdp-be/scripts/seed_segment_v0_local.sql): `seg_000001` has different meanings, so assign one approved definition before loading. Treat the `seg_900001`–`seg_900003` IDs in the 1M fixture as test-only. Record expected raw and consented counts for the agreed rules. Decide whether the separate [card activity fixture](../services/ecodai/internal/features/segments/testdata/card_activity_local.sql) is wanted; it has only 120 members and must not silently change the million-member scenario.
2. **Prepare the serving schema and API.** Adapt the versioned v0 schema in [eco migration 000003](../services/ecodai/migrations/000003_segment_v0.up.sql) and the catalogue changes in [eco migration 000004](../services/ecodai/migrations/000004_attribute_segments.up.sql) into new `cdp-be` forward migrations. Adapt the v0 list, selection, estimate, request-status, and export paths to use `kind`, option IDs, count provenance, `base`, and a pinned READY `build_id`. Leave unrelated `cdp-be` tables and its v1 segment flow alone. Do not add a refresh or build worker to the service.
3. **Recreate the disposable database.** Drop and recreate the dedicated test database, then run `cdp-be` migrations from the beginning. Apply the new forward migrations. Check that the service starts against the empty segment read model before loading data.
4. **Load definitions, then member facts.** Load the approved category and option catalogue first, followed by agreed predefined definitions. Adapt the [1M synthetic fixture](../services/ecodai/internal/features/segments/testdata/scale_1m.sql) to insert exactly 1,000,000 unique members into `member_facts_v0` under one new `build_id` and fixed `source_date`. Its present inserts into `member_cookbook_v0` and dated `segment_members_v0` are legacy test data and must not be treated as a published build. Populate current consent and any required org, retail, product, or predefined relationships explicitly; do not invent missing relationships from the fixture.
5. **Prepare outputs outside `cdp-be`.** The load process records source completion, derives option IDs and any required memberships, computes stored catalogue counts, and validates SQL results. For this first 1M run, serve request counts with SQL. Generate ordinal mappings and Roaring bitmaps offline only if a measured query needs them; if generated, reconcile exact member IDs against the same build's SQL results. No `cdp-be` refresh job is involved.
6. **Validate, then publish.** Check source totals, foreign references, definition versions, consent, representative exact ID sets, and overlapping AND/OR counts. The 1M fixture should yield 1,000,000 all members, 500,000 active-card members, and 587,569 members with income at least 100,000 before consent filtering. Once all required outputs pass, mark the build READY and advance `segment_current_build_v0` in one transaction. A failed load leaves the prior READY build current.
7. **Exercise serving and export.** Verify segment list/get, an `all_members` selection, option and predefined counts, dynamic SQL filters, request status, and a full export. Pin each request or export to one build; the export job streams IDs and checks authoritative current consent. Measure count latency, database plans, worker memory, export time, and results at 1M. A corrected same-day load gets a new `build_id`; compare results before and after publication.

## Completion criteria

The reset is repeatable from an empty test database. Catalogue IDs and definitions are unambiguous; counts and representative ID sets match the source build; published requests stay on one build; a failed load cannot replace the current build; and the API performs no background member refresh. The 1M result is a functional and initial performance check, not evidence for 5M–20M capacity or production member access.
